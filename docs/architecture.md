# Архитектура DSH Mobile

Документ описывает, как устроен мобильный клиент, почему выбраны именно такие
решения и где проходят границы надёжности. Ссылки на исследование API DSH —
в `research/session-api.md`, `research/plugin-authoring.md`,
`research/test-instance.md`; протокол — в `docs/mobile-api.md`.

## 1. Цели и ограничения

Цели:

1. Управлять **живыми** сессиями DeepSeek Harness с Android-телефона: смотреть
   историю, отправлять промпты, останавливать ход, отвечать на approvals.
2. **Не тратить токены** на синхронизацию: клиент — наблюдатель существующего
   журнала; просмотр истории не должен приводить ни к одному запросу к модели.
3. Корректно работать на **раскладных** устройствах (Honor Magic V3 и похожие):
   две панели на внутреннем экране, одна на внешнем, без потери состояния.
4. Не трогать shipped-код DSH: расширение — только через штатный механизм плагинов.

Ограничения, заданные средой:

- апстрим DSH — Electron-приложение 0.2.1-rc.2, исходники доступны только как
  собранный `app.asar` (мы его распаковали в `research/app`);
- на машине нет JDK/Android SDK → APK здесь не собирается, но исходники и CI есть;
- в песочнице нет браузера → визуальная проверка CSS/шва остаётся на устройстве;
- LAN-listener не должен открывать RCE: доступ только к узкому мобильному API,
  никакого проксирования произвольных методов хоста.

## 2. Общая схема

```
┌───────────────────────────── Android / раскладной ─────────────────────────────┐
│  PWA (web/)                       APK-обёртка (android/)                        │
│  ─ hash-роутер, store, IndexedDB  ─ WebView, pairing-экран, dshm:// deep links  │
│  ─ api.js (Bearer, JSON)          ─ тот же PWA по LAN-URL                       │
│  ─ sse.js (fetch-stream, курсор)                                                │
└───────────────────────────────────┬─────────────────────────────────────────────┘
                                    │ Wi-Fi, HTTP(S), Bearer device-token
┌───────────────────────────────────▼─────────────────────────────────────────────┐
│  DSH host (Windows/Electron, in-process Cordis)                                 │
│                                                                                 │
│  dsh-mobile plugin (lib/index.js)                                               │
│   ├─ GatewayServer (src/server.js)  :3081  ─ PWA static + /api/v1 + SSE         │
│   ├─ ApiRouter (src/routes.js)      ─ auth, идемпотентность, лимиты, gzip/br    │
│   ├─ StreamHub (src/sse.js)         ─ один поток на (device, session), heartbeat │
│   ├─ AuthManager/DeviceStore         ─ pairing-коды, токены, rate-limit          │
│   ├─ SessionBridge (src/session-bridge.js)                                      │
│   │    ├─ ctx.sessionController.list   ─ список (cold-safe, без активации)      │
│   │    ├─ ctx.sessionQuery.observeSession ─ чтение журнала без promotion        │
│   │    ├─ ctx.on('session/event')       ─ durable-дельты по seq                 │
│   │    ├─ ctx.on('agent/assistant-stream') ─ живой текст                        │
│   │    ├─ ctx.sessionController.prompt/cancel/updateQueue                       │
│   │    └─ ctx.approval waterfall (prepend) ─ релей approvals                    │
│   └─ /m/pair на родном loopback-origin (cookie DSH, ctx.connection)             │
└─────────────────────────────────────────────────────────────────────────────────┘
```

Ключевое свойство: PWA и API отдаются **одним origin** (`http://<PC>:3081`).
Браузер не делает cross-origin запросов, cookie не нужны — только Bearer.
Pairing-страница живёт на *другом* origin — родном loopback-порту DSH, где уже
есть аутентификация владельца; поэтому код привязки физически не может утечь в LAN.

## 3. Почему плагин, а не отдельный сервер-компаньон

Рассматривались три варианта:

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **A. Плагин в процессе DSH** (выбран) | прямой доступ к сервисам, тот же auth, ноль сетевых хопов, нет дублирования состояния | требует установки в профиль; код плагина живёт в профиле | ✅ |
| B. Внешний компаньон + реюз Typert/`/api` DSH | ничего не ставим в DSH | нужно реализовать Typert-клиент, добыть launch-token, два процесса, хрупко к версии | ❌ |
| C. Форк/патч shipped-кода | полный контроль | ломается при обновлении, нелегально по духу продукта | ❌ |

Вариант A подтверждён экспериментом (`research/plugin-spike`): плагин грузится
из профиля, регистрирует маршруты на родном web-сервере, поднимает собственный
сокет и корректно выгружается.

## 4. Синхронизация сессий

### 4.1 Два вида состояния

1. **Durable-журнал** — append-only JSONL (zstd) с плотной нумерацией `seq`,
   источник истины. Читается через `sessionQuery.observeSession` (cold-safe:
   не «промоутит» агента, не пишет в журнал).
2. **Живые события** — корневая шина `session/event`; приходят с тем же `seq`.

Поток в PWA устроен так:

```
GET /sessions/{id}?turns=1        → окно: последние ~35 событий + cursor
GET /sessions/{id}/stream?cursor  → SSE: hello, delta*, live*, state*, approval*, ping*, resync
```

- Курсор — последний применённый `seq`. Реконнект всегда `?cursor=last`.
- `delta` — durable-события строго по одному, с проверкой плотности: если
  пришёл `seq > last+1`, сервер шлёт `resync`, клиент перезапрашивает окно.
- `live` — транзиентные чанки ассистента (`text-delta`): не сохраняются и при
  реконнекте не повторяются; после завершения шага приходит durable
  `assistant/message`, и текст уже консистентен.
- `state` — `running`/`idle`; `approval` — запрос/снятие approval.
- `ping` каждые 15 с; сервер не держит буфер > 256 КБ на клиента (медленный
  читатель отключается, клиент догоняет по курсору).

### 4.2 Почему НЕ `sessionController.follow()`

Документация и код DSH показывают: `follow()` у холодной сессии вызывает
`promote()` → `ctx.agents.resume()`. Это публикует живого агента и может
дописать synthetic crash-repair события в **durable** журнал. Для мобильного
наблюдателя это недопустимо: просмотр не должен менять состояние хоста.
Поэтому мост использует `observeSession` + шину событий.

### 4.3 Размер окна и «лишние токены»

- Окно: до 8 сообщений, ≥1 хода, но **жёсткий кап 40 событий**; если кап
  срезал начало хода, назад добавляется ближайший `user/message` (+2 события
  контекста), чтобы телефон всегда открывался на реплике пользователя.
- Превью инструментов: аргументы ≤ 600 Б, результаты ≤ 1024 Б, полный вывод не
  передаётся (флаг `truncated`).
- Заголовки сессий берутся из projection-кэша DSH; если его нет — из события
  `session/title` при открытии (без LLM). `sessionTitle.refresh()` не вызывается.
- Запрещённые операции зафиксированы в `docs/mobile-api.md` §6 и в
  комментариях `session-bridge.js`.

### 4.4 Холодный старт и офлайн

PWA хранит в IndexedDB: список сессий, последние 50 событий на 10 сессий,
курсоры, черновики, настройки. Холодный старт — мгновенно из кэша, затем
ревалидация списка и окна. Нет polling: только SSE + явные действия.
При `visibilitychange`/`offline` поток закрывается, курсор сохраняется.

## 5. Безопасность

Модель угроз: LAN-сосед, злоумышленник с доступом к Wi-Fi, забытое устройство.

| Угроза | Мера |
|---|---|
| чужой браузер в LAN | Bearer device-token; без него 401 на всё, кроме `/hello`, `/pair`, статики |
| подбор pairing-кода | 8 символов из 32-буквенного алфавита, TTL 5 мин, 5 попыток, rate-limit 10/мин на IP, код одноразовый |
| перехват кода на ПК | код показывается только на loopback-странице `/m/pair` (cookie DSH, `ctx.connection.requestRejection`) |
| утечка токена из файла | в `mobile-remote.json` только SHA-256 токена; сравнение timing-safe |
| забытое устройство | отзыв на `/m/pair` или `POST /devices/revoke`; удаление записи + 401 |
| подделка Host/Origin | LAN-listener не использует cookie; CORS `*` без credentials, Authorization-only |
| RCE через API | узкий протокол: list/open/older/stream/prompt/cancel/approval/question/workspaces/jobs — нет произвольных вызовов сервисов |
| path traversal в статике | `resolve` + проверка префикса корня |
| большие тела запроса | лимит 512 КБ на JSON, 403/413 |

Отдельно: плагин не читает `~/.dsh/.credentials.yaml`, не экспортирует
переменные, не пишет в сессии. Вся «власть» — вызовы публичных сервисов DSH.

HTTP по LAN: токен летит открытым текстом. Для домашней сети это осознанный
компромисс (как у многих локальных пультов). Для недоверенной сети: TLS в
конфиге плагина или туннель (Tailscale/Cloudflare), тогда PWA ещё и ставится
как standalone (service worker требует secure context).

## 6. Approvals и вопросы

DSH не имеет API «получить/ответить на approval по id». Единственный путь —
waterfall `approval/request`, в котором отвечает десктопный GUI. Мост
регистрируется `{ prepend: true }` и:

1. всегда запоминает запрос (для отображения на телефоне);
2. если десктопный клиент подключён (`typertGateway.hasLiveClient()`), просто
   вызывает `next()` — отвечает GUI, телефон показывает «решается на ПК»;
3. если десктоп не подключён — ретранслирует запрос в SSE (`approval`) и ждёт
   ответа телефона до 120 с; `allow → allowed-once`, `deny → rejected`,
   таймаут → `cancelled` (вопрос снимается, турн не висит).

`remember`/«разрешить всегда» не поддерживается: в DSH-политике только
`ask`/`never`, а outcome-словарь — `allowed-once|rejected|cancelled|unavailable`.

Вопросы `ask_user` в v1 только отображаются: ответ требует живого корневого
агента и превращается в model-visible сообщение (токены + сложная семантика).
Ответ — на десктопе; в UI кнопка ведёт к объяснению.

## 7. Раскладные устройства

- Две панели всегда в DOM; posture меняет только CSS Grid. SSE, черновик,
  скролл и открытая сессия не пересоздаются.
- Ширины колонок: `env(viewport-segment-width 0 0)`, `env(viewport-segment-width 1 0)`,
  gutter = `max(16px, env(viewport-segment-left 1 0) − env(viewport-segment-right 0 0))`.
- Медиа: `(horizontal-viewport-segments: 2)`, `(spanning: single-fold-vertical)`,
  `(spanning: dual-screen)`; порог планшета 840dp; safe-area для внешнего экрана.
- Layout Lab (`?demo=1&lab=1`) симулирует 1/2 сегмента и шов 0–48 px на обычном
  экране — так проверяется вёрстка без устройства.
- Требования к Android-обёртке: `resizeableActivity=true`, `configChanges` для
  ориентации/размера/клавиатуры, edge-to-edge insets; WebView растягивается на
  оба сегмента, CSS делает остальное.

## 8. Отказоустойчивость

| Отказ | Поведение |
|---|---|
| LAN-порт занят | плагин логирует предупреждение, DSH продолжает работать; порт меняется в конфиге |
| host не имеет `sessionController` | мобильные сессии отвечают `unsupported`, pairing и PWA работают |
| сервис появился позже | ленивый мост переразрешает `sessionController` при первом запросе |
| мобильный клиент отвалился | SSE-поток закрывается, буфер не растёт, повторный вход по курсору |
| дубль потока с того же устройства | старый поток закрывается (`superseded`) |
| рестарт DSH | устройство остаётся привязанным (файл в `$DSH_HOME/mobile-remote`), клиент переподключается по сохранённому URL |
| смена LAN-IP ПК | в настройках PWA адрес меняется; pairing-страница показывает актуальные адреса |

Диагностика: `<DSH_HOME>/logs/dsh-mobile.log` — плагин сам ставит файловый
экспортёр (в штатном web-профиле нет консольного логгера).

## 9. Совместимость

Проверено на DSH `0.2.1-rc.2` (Cordis 4.0.5), профиль `desktop`, Windows.
Плагин использует только документированные сервисы (`sessionController`,
`sessionQuery`, `sessionProjections`, `agents`, `approval`, `workspaceRegistry`,
`jobs`, `webServer`, `connection`) и не патчит чужие модули. При обновлении DSH:

1. сверьте `compatibility.json` (версия plugin API);
2. проверьте, что `sessionQuery.observeSession` и форма событий не изменились;
3. прогоните `node scripts/run-tests.mjs` (20 тестов) и e2e-скрипт
   `research/tools/e2e-mobile.mjs` на изолированном инстансе.

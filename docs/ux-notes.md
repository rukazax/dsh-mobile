# DSH Mobile — UX и инженерные заметки

Статус: реализация PWA-клиента (`packages/dsh-mobile/web`). Контракт — `docs/mobile-api.md`,
версия протокола `1`. Документ описывает решения по раскладке, жестам, синхронизации
и байтовому бюджету, а также границы проверенного.

## 1. Как посмотреть

```powershell
# из корня репозитория
cd packages\dsh-mobile\web
C:\Users\<user>\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe -m http.server 8765 --bind 127.0.0.1
```

- Демо (главный путь ревью): <http://127.0.0.1:8765/?demo=1>
  Открывается сразу живой диалог `s-demo-1`: список из 8 сессий, стрим, tool-карточки.
  В демо работают: отправка промпта (send / queue / steer), стоп, подтверждение (`s-demo-2`),
  вопрос (`s-demo-6`), создание сессии, поиск, настройки, смена языка/темы/размера текста.
- Layout Lab (эмуляция раскладной): <http://127.0.0.1:8765/?demo=1&lab=1>
  Слева/сверху панель: раскладка (1 сегмент / 2 сегмента / планшет), ширина, шов (0/16/24/48 px),
  поза, сброс. Рамка вокруг — симуляция устройства. Демо внутри кадра живое.
- Без демо: <http://127.0.0.1:8765/?demo=0> — экран сопряжения (нужен реальный шлюз).
- Параметры: `?lang=en`, `?theme=dark|light|auto` — для ревью.
- Для установки PWA нужен HTTPS или localhost (service worker). На LAN-HTTP работает
  APK-обёртка вокруг тех же файлов; SW в этом случае не регистрируется осознанно.

Проверка, что статика раздаётся: `/`, `/manifest.webmanifest`, `/sw.js`, `/styles/*.css`,
`/js/*.js`, `/icons/*.png` → 200 (см. §11).

## 3. Раскладка и раскладушки

Ключевое решение: **обе панели всегда в DOM**. Раскладка — только CSS, поэтому смена
позы/ориентации не пересоздаёт разметку и не сбрасывает состояние (черновик, скролл,
открытую сессию, живой SSE-поток).

- **Сложен / узкий экран.** Одна панель; `#app[data-view="list"|"chat"]` переключает
  список и диалог слайдом (`transform` + `visibility`, чтобы скрытая панель уходила
  и из tab-порядка). Кнопка «назад» в шапке диалога — только в однопанельном режиме.
- **Раскрыт (2 сегмента).** Медиа-запросы:
  `@media (horizontal-viewport-segments: 2)`, `@media (spanning: single-fold-vertical)`,
  `@media (spanning: dual-screen)`. Сетка `grid-template-columns` = ширина сегмента 0,
  шов, ширина сегмента 1, где ширины берутся из `env(viewport-segment-width 0 0)`,
  `env(viewport-segment-width 1 0)`, а шов — `max(16px, env(viewport-segment-left 1 0) −
  env(viewport-segment-right 0 0))`. Контент физически не может пересечь шов: панели
  стоят в разных колонках, между ними отдельная колонка-гуттер с волосяной линией.
- **Планшет / широкий экран (≥ 840 dp).** Постоянный rail: список 300–340 px + диалог.
  Это правило объявлено раньше фолдабл-правил, поэтому на раскрытой раскладушке
  двухпанельный режим выигрывает каскадом.
- **Safe areas.** `env(safe-area-inset-*)` для внешнего экрана с вырезом: шапки, composer,
  нижние отступы списка, листы и оверлеи.
- **Клавиатура.** `--app-h` выставляется из `visualViewport.height` (resize/scroll) —
  composer остаётся над клавиатурой, `100dvh` не «прыгает».
- **Honor Magic V3.** Внутренний экран даёт 2 вертикальных сегмента (список слева, диалог
  справа), внешний — один сегмент со слайд-навигацией. В реальном браузере это проверяется
  диагностикой в настройках: `matchMedia('(horizontal-viewport-segments: 2)')`,
  `matchMedia('(spanning: single-fold-vertical)')` и фактическое значение
  `env(viewport-segment-width 0 0)` (проба в `lab.js`).

### Layout Lab (`?lab=1`)

Реальные сегменты нельзя включить на обычном мониторе, поэтому Lab выставляет те же
CSS-переменные вручную: `data-lab-layout="single|dual|rail"`, `--lab-w`, `--lab-hinge`,
`data-lab-posture`. Переключение раскладки не трогает JS-состояние — ровно как на устройстве.
Проверка «что смотреть»: откройте сессию, наберите черновик, прокрутите, включите стрим,
переключите 2 сегмента ↔ 1 — черновик, позиция и поток должны остаться.

## 4. Жесты и клавиатура

| Действие | Где | Поведение |
|---|---|---|
| Тап по сессии | список | открыть диалог (на фолде — слайд вправо) |
| «Назад» | шапка диалога | к списку; сессия и поток остаются живыми |
| Pull-to-refresh | список, скролл вверху | обновить список (`GET /sessions`) |
| Скролл вверх | диалог | автопрокрутка отключается; появляется «К последнему» с числом новых |
| Ctrl/Cmd+Enter | composer | отправить (Enter — перенос строки) |
| Ctrl/Cmd+J | диалог | к последнему сообщению |
| Escape | оверлеи/листы | закрыть |
| Тап по tool-карточке | диалог | раскрыть аргументы/результат (`<details>`, нативно доступно) |
| Чипы send/queue/steer | composer, только пока агент работает | режим следующего промпта |

## 5. Синхронизация (контракт §4.3, §7)

- **Поток.** `fetch('/sessions/{id}/stream?cursor=<seq>')` + `ReadableStream`, а не
  `EventSource` — нужен `Authorization: Bearer`. Парсер собирает кадры по `\n\n`,
  корректно склеивает кадры, разрезанные между чанками (проверено интеграционным тестом).
- **Курсор.** Последний `seq` из `hello.cursor` и `delta.events[].seq`; хранится в
  IndexedDB (`cursor:<id>`) с debounce 400 мс. Реконнект всегда идёт `?cursor=<last>`,
  сервер досылает только дельту — транскрипт целиком не перезапрашивается.
- **Дедупликация.** События дедуплицируются по `seq`; снапшот и кэш сливаются по `seq`
  (свежий выигрывает).
- **`resync`.** Полный снапшот `GET /sessions/{id}?turns=2`; счётчик ресинков в диагностике.
- **Backoff.** 700 мс × 2^attempt, кап 15 с, jitter ±30 %; сброс при открытии потока.
  Watchdog: нет данных 70 с → переподключение (сервер шлёт `ping` каждые 15 с).
- **Фон.** `visibilitychange`/`offline` → поток закрывается, статус «на паузе», курсор
  сохранён; возврат/`online` → немедленный реконнект с курсором. Опроса нет.
- **Один поток на сессию.** Переход в список поток не рвёт (обе панели живут), поэтому
  статус сессии в списке обновляется из `state`-событий.
- **Холодный старт.** Сначала `db.readSessions()` → мгновенный список из кэша
  (метка «из кэша»), затем `GET /sessions`; для сессии — кэш событий → снапшот → поток.
- **Черновики.** Пишутся в IndexedDB с debounce 400 мс, восстанавливаются при открытии.
- **Прочитано.** `POST /read {lastSeenSeq}` с debounce 1.5 с, только если пользователь
  у конца диалога и вкладка видима.

## 6. Экономия трафика и токенов

Правила контракта §6 соблюдаются: клиент не вызывает заголовки/суммаризацию/`resume`,
не шлёт полный транскрипт, не опрашивает сервер, не запускает промпты сам.

- Список: один `GET /sessions?limit=50` при открытии/возврате/ручном refresh/pull;
  поиск фильтрует локально и (через 450 мс) уточняет серверным `q` — это чтение лога, не LLM.
- Открытие сессии: `turns=2` (по контракту), дальше только дельта по курсору.
- История: `GET /older` только по явному тапу «Показать старше», страницами по 3 хода.
- Tool-результаты — только превью ≤ 2 КБ (как отдаёт шлюз), в UI бейдж «обрезано».
- SSE-события обрабатываются инкрементально: live-чанки коалесцируются в один пузырь
  (обновление через `requestAnimationFrame`), durable-события добавляются DOM-узлами,
  полный ре-рендер — только для снапшота/смены языка.
- `requestId` (UUID) на каждый POST — идемпотентные повторы безопасны.
- Бюджет §7 (после gzip) — зона ответственности шлюза; клиент не запрашивает ничего
  сверх перечисленного.

Измеренный вес клиента (unminified, без сжатия):

| Файл | Размер | gzip |
|---|---|---|
| весь JS (15 модулей) | ~200 КБ | ~51 КБ (brotli ~42 КБ) |
| `chat.js` | ~38 КБ | ~9 КБ |
| `i18n.js` (ru+en) | ~38 КБ | ~11 КБ |
| `demo.js` (мок) | ~26 КБ | ~7 КБ |
| CSS (3 файла) | ~50 КБ | ~10 КБ |
| `index.html` | ~7.5 КБ | ~2.4 КБ |

Целевые «< 120 КБ JS unminified» **не достигнуты**: полноценные две локали (~38 КБ),
демо-мок (~26 КБ) и комментарии (~15 КБ) дают ~200 КБ. На провод уходит brotli/gzip
(~42–51 КБ) и только один раз — SW кэширует оболочку. Если цель по исходникам жёсткая,
следующие шаги: вынести данные демо в JSON (только демо), удалить комментарии,
сократить словарь i18n. Это осознанный компромисс в пользу читаемости: сборки нет,
и Lead читает исходники глазами.

## 7. Доступность и тач

- Все интерактивные элементы ≥ 44 dp (`--tap`).
- `aria-live` регион: старт/конец стрима и новые сообщения анонсируются один раз,
  сам поток — `aria-live="off"` (иначе скринридер захлёбывается).
- `focus-visible` кольца заданы явно; оверлеи/листы закрываются Escape, фокус ставится
  на первый элемент, `role="dialog"`, `aria-modal`.
- `prefers-reduced-motion` отключает анимации, курсор и pulse-точки.
- Семантика: `<main>`, `<section aria-label>`, список сессий — `role="list"`/`listitem`,
  кнопки с `aria-label`, `aria-current` на активной сессии.
- Чипы режимов — `role="radio"`/`aria-checked`.
- Контраст: пары токенов проверены визуально; текст на акценте — белый.

## 8. i18n

- Русский по умолчанию, английский переключается в настройках (`dshm.lang`).
- Все строки — в `js/i18n.js`; компоненты не содержат копирайта. Множественные формы:
  ru (3 формы) и en (2) через `tn()`.
- Даты/время — `Intl.DateTimeFormat`/`Intl.RelativeTimeFormat` с локалью, без ручных строк.
- Демо-данные (названия сессий, тексты) — это данные, а не UI-строки; часть демо-копирайта
  берётся из словаря (`demo.*`), чтобы переключение языка работало и в демо.

## 9. PWA и APK

- `manifest.webmanifest`: standalone, `orientation: any` (важно для раскладушки),
  иконки 192/512 + maskable, shortcuts «Список сессий» и «Новая сессия»
  (`#/sessions?new=1`).
- `sw.js`: версионированный кэш `dshm-shell-v1`; навигация — network-first с офлайн-
  заглушкой; статика — stale-while-revalidate; `/api/**` и `/stream` **никогда** не
  кэшируются и не перехватываются (важно: API может быть на другом origin).
- URL-ы относительные — PWA работает и из подкаталога, если шлюз раздаёт её не с корня.
- APK-обёртка (другой владелец) грузит те же файлы; при HTTP SW не регистрируется.

## 10. Соответствие контракту

| UI-действие | Эндпоинт |
|---|---|
| сопряжение | `POST /pair`, затем `GET /sessions` |
| список, поиск, refresh | `GET /sessions?limit=&q=` |
| открытие сессии | `GET /sessions/{id}?turns=2` |
| поток | `GET /sessions/{id}/stream?cursor=` |
| история | `GET /sessions/{id}/older?before=&turns=` |
| промпт send/queue/steer | `POST /sessions/{id}/prompt {requestId,text,mode}` |
| стоп | `POST /sessions/{id}/cancel {requestId,scope:"turn"}` |
| подтверждение | `POST /sessions/{id}/approval {requestId,approvalId,decision,remember?}` |
| вопрос | `POST /sessions/{id}/question {requestId,questionId,answer}` |
| прочитано | `POST /sessions/{id}/read {lastSeenSeq}` |
| новая сессия | `POST /sessions {requestId}` |
| отзыв устройства | `POST /devices/revoke` |
| диагностика | `GET /hello`, `GET /health` (health не вызывается автоматически) |

Коды ошибок маппятся в человеческие сообщения (`api.errorText`): `auth-*` → повторное
сопряжение, `pairing-invalid/expired`, `rate-limited`, `session-not-found`, `agent-busy`,
`prompt-invalid`, `approval-unknown`, `unsupported`, `internal`, сеть/таймаут.

## 11. Что проверено, а что нет

Проверено (в этой среде):

- `node --check` — все 15 ES-модулей + `sw.js` (синтаксис).
- Статический анализ ссылок: каждый named-import существует в целевом модуле;
  все `t('...')`-ключи есть в словаре; проверка ключей, собираемых динамически.
- HTTP: `/`, `/manifest.webmanifest`, `/sw.js`, `/styles/tokens.css`, `/js/main.js`,
  `/icons/icon-512.png`, `/offline.html` → 200 с корректными Content-Type.
- Headless-прогон реальных модулей на DOM-шиме (Node): демо-режим — 33/33 проверки,
  lab-режим — 40/40, интеграция с мок-шлюзом — 20/20, ноль `console.error`:
  список, снапшот, живой SSE (включая кадры, разрезанные между чанками), дедуп/замена
  live на durable, tool-карточки, листы approval/question с POST, composer send/queue,
  стоп, поиск, роутер, markdown (экранирование XSS), ru-плюрализация, переключение языка.
- SSE-реконнект: после закрытия сервером клиент переподключился с `cursor=2` и показал
  дельту.
- Pairing-flow: ввод кода → `POST /pair` → Bearer-токен → список; 401 → очистка токена
  и возврат на экран сопряжения.
- Иконки сгенерированы Pillow и визуально проверены (PNG 512).

**Не проверено (честно):**

- Реальный браузер/Magic V3: в этой среде Chrome/Edge не запускаются (песочница запрещает
  named pipes), поэтому **CSS-раскладка, шов, шрифты, скролл и клавиатура визуально не
  проверены**. Логика раскладки — только по коду; Layout Lab предназначен для этой проверки.
- Service worker в браузере (кэш/офлайн/установка) не прогонялся.
- Реальный IndexedDB-путь не исполнялся: в шиме `indexedDB` отсутствует, работал
  memory-fallback. Код транзакций написан с учётом «не ждать между запросами», но проверить
  это можно только в браузере.
- Реальный шлюз `packages/dsh-mobile` не поднимался: интеграция — против мока,
  реализующего контракт §3–4 (кто-то другой пишет сервер; тест с ним — следующий шаг).
- `GET /sessions/{id}/events/{seq}` (v1.1), attachments, jobs UI — вне v1/PWA.
- Push, share_target, сканер QR (без зависимостей камеру не подключали): QR-ссылка
  `dshm://pair?...` вставляется текстом и парсится.
